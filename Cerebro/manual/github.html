      Capítulo 5

      GitHub sin miedo

      GitHub es el lugar donde vive el cerebro. Guarda cada versión de cada archivo, deja ver qué cambió y quién lo cambió, y permite revisar los cambios antes de aceptarlos.

      Por qué el cerebro vive en GitHub

      Historial completo

      Cada cambio queda guardado. Siempre puedes ver o recuperar cómo estaba una página hace una semana.

      Revisión antes de aceptar

      El agente propone; tú decides. Nada entra en la versión principal sin tu visto bueno.

      Disco duro de la nube

      Las sesiones de Claude Code en la nube se borran. Lo que no se sube a GitHub, se pierde. Ver La nube.

      Colaboración

      El otro socio podrá ver y proponer cambios sobre el mismo cerebro.

      Los conceptos, uno por uno

      Repositorio
      La carpeta del proyecto en GitHub, con todo su historial. El de Arvyon es arvyonfoa/Arvyon: arvyonfoa es el dueño y Arvyon el nombre. Contiene README.md, Raw/ (la presentación) y Cerebro/.
      Commit
      Una foto guardada de los cambios, con un mensaje que explica qué se hizo y por qué. Ejemplo real: baf8201 Fase 1 (aprender, 9 nov-15 dic): prompt maestro, guía de la Etapa 1 y competencia. El código de 7 letras es su identificador.
      Rama (branch)
      Una línea de trabajo paralela. Permite hacer cambios sin tocar la versión principal hasta que estén listos. Es como trabajar en una copia del cuaderno y, al final, pasar al original solo lo que se aprobó.
      main
      La rama principal: la versión oficial del cerebro. Es la que ves en GitHub por defecto y la que descargas a Obsidian.
      Push y pull
      Push es subir commits de una máquina a GitHub. Pull es bajar a tu computador los cambios que hay en GitHub.
      Pull request (PR)
      Una solicitud para unir los cambios de una rama a main. Muestra exactamente qué archivos cambian y permite comentar antes de aceptar. Se puede unir (merge) o cerrar sin unir.
      Diff
      La comparación línea por línea entre el antes y el después. En verde lo que se añade; en rojo lo que se quita.
      Merge (unir)
      Juntar los cambios de una rama con otra. Al unir un PR, sus cambios pasan a main.
      Conflicto
      Cuando dos ramas cambian las mismas líneas de forma distinta y Git no sabe cuál quedarse. Hay que elegir a mano. El agente puede resolverlos.
      Revert
      Un commit nuevo que deshace otro commit, sin borrar la historia. Es la forma segura de deshacer.
      Force push
      Subir cambios reescribiendo la historia de una rama. Es peligroso porque puede borrar trabajo; por eso Claude Code lo tiene bloqueado y usa revert en su lugar.
      Clonar
      Descargar una copia completa del repositorio a tu computador (lo que haces con GitHub Desktop).

      El ciclo de un cambio

      1. Le pides algo al agente en Claude Code.
      2. El agente trabaja en su rama (en este proyecto, claude/magical-bohr-5nj070) y hace commits.
      3. Hace push: los commits suben a GitHub, a esa rama.
      4. Abre un pull request hacia main, o añade los commits a uno que ya esté abierto.
      5. Tú revisas el PR en GitHub y decides: unir, pedir cambios o cerrar.
      6. Si lo unes, los cambios están en main. En tu computador haces pull para verlos en Obsidian.

      Cómo revisar y decidir un pull request

      1. Abre el PR en GitHub (te llega el enlace en el chat o en Pull requests del repositorio).
      2. Lee la descripción: qué cambia y por qué.
      3. Abre la pestaña Files changed y mira el diff de los archivos que te importan.
      4. Si algo no te gusta, díselo al agente en el chat (o deja un comentario en el PR) y espera la corrección.
      5. Si todo está bien, pulsa Merge pull request y confirma.
      6. Si ya no quieres esos cambios, pulsa Close pull request. No se pierde nada: el PR queda cerrado y se puede consultar.

      Reglas para decidir con coherencia

      1. main es la verdad oficial. Lo que no está en main todavía es una propuesta.
      2. Un PR, un tema. Es más fácil revisar cambios pequeños y con un objetivo claro.
      3. Revisa antes de unir. Al menos la descripción y los archivos principales.
      4. No dejes PR abiertos mucho tiempo. Cuanto más esperan, más probable es un conflicto.
      5. Deshaz con revert, nunca reescribiendo la historia.
      6. Un PR unido está terminado. El trabajo nuevo va en un PR nuevo.
      7. Nunca subas claves ni contraseñas al repositorio. Para eso existen los secretos de red.

      Quién puede hacer qué

      Claude Code entra a GitHub con la app de Claude para GitHub, que tú autorizaste para el repositorio arvyonfoa/Arvyon. En la nube, tus credenciales reales nunca entran en la máquina: un proxy de GitHub las pone por fuera. Ese proxy no permite borrar ramas ni subir etiquetas, y solo da acceso a los repositorios conectados a la sesión.

      Quien une los PR eres tú

      El agente puede abrir, actualizar y comentar pull requests, pero la decisión de unir o cerrar es tuya.
